# 0008 — TileMap：每层一个节点，格子存在类型化数组里，每个区块一个 Mesh 渲染

**Status:** Accepted (2026-10-09)

## Context

横版平台游戏（“马里奥”）需要 TileMap：关卡是一张格子表，一层几千到几万格，引擎目前没有。

Godot 的做法（4.3 起）：`TileSet` 资源描述图块和每个图块的属性，每层一个 `TileMapLayer` 节点；渲染按区块合批；
碰撞时根据图块的碰撞多边形自动在物理引擎里生成静态物体。

`spikes/tilemap/REPORT.md` 在 iPhone 17 小游戏（无 JIT、WebGL1）上比较了五种 Pixi 画法。地图 512 × 32 格、3 层：

- 每格一个 Sprite：稀疏地图每帧绘制 9.4 ms，满地图只有 19 fps。
- 按区块隐藏屏幕外的部分不够：镜头一动，同一个 render group 里所有精灵都要重算变换（满地图 19.6 ms）。
- 每个 16×16 区块一个 Mesh 最好：每帧绘制 2.6 ms（满地图 3.7 ms），p95 最稳，建图比用精灵快 10 倍，改一格约 0.1 ms。

## Decision

### 数据

- **`TileSet`**：一张图集贴图、格子边长 `tileSize`、每个图块的属性（碰撞类型、自定义字段）。多个关卡、多个层可以共用。
  一个 TileSet 只对应一张贴图（一个 Mesh 只能用一张贴图）。
- **`TileMapLayer`**（`Node2D`）：一层格子，引用一个 TileSet。大小在创建时固定（`width × height` 格），格子存在 `Uint16Array` 里：0 是空，其他值是图块编号。
  多层就是多个节点，叠放顺序由场景树决定。
- 接口照搬 Godot 的名字：`setCell` / `eraseCell` / `getCell` / `localToMap` / `mapToLocal` / `getUsedRect`，以及读图块属性的方法。
  地图外的格子算空。
- 数据和碰撞在无头模式下照常可用；只有渲染依赖 Pixi（ADR 0002）。

### 渲染

- 地图按 16 × 16 格分成区块，每个区块一个 Pixi `Mesh`：
  - 顶点缓冲区的容量固定为 256 个四边形，空格子写成面积为 0 的四边形；
  - 索引用 `Uint16Array`（iOS 小游戏的 WebGL1 没有 32 位索引）；
  - 改一格只重写这个格子的 16 个浮点数，并标记区块需要上传；
  - 屏幕外的区块 `visible = false`。可见范围由视口（以后是 Camera2D）换算到这一层的局部坐标得出。
- 按 ADR 0002 的方式同步：节点只持有格子数据和“哪些区块变了”；`PixiRenderer` 给 `TileMapLayer` 一个内容层（和 Sprite2D 的 sprite 一样），在里面创建和更新区块 Mesh。
- 像素风：TileSet 的贴图用最近邻采样；图层的位置在绘制时对齐到物理像素。
- 销毁时先销毁区块 Mesh，再释放贴图（否则 Pixi 会警告贴图还绑在着色器上）。贴图本身由资源系统管理，不跟着图层销毁。

### 碰撞

- **不自动生成物理体**，这一点和 Godot 不同。图块的碰撞属性只有“整格实心”和“单向平台”，不支持任意多边形。
- `TileMapLayer` 对外提供按格子查询碰撞的内部接口（格子边长 + 某一格的碰撞类型），供 `CharacterBody2D` 使用。
  为什么这样做、限制在哪里，见 ADR 0009。

### 制作关卡

- 引擎不做编辑器、不做自动拼接（terrain / autotile）。关卡用 Tiled 或 LDtk 编辑，导入它们导出的 JSON，生成 TileSet 和各层。
- 对象层（敌人、金币、出生点）导入成普通数据，由游戏自己创建节点；不支持“格子里放场景”。

### 第一版不做

动画图块、一个 TileSet 用多张贴图、图块翻转和旋转、斜 45° / 六边形地图、按 y 排序。
动画图块和翻转以后按下面 `@pixi/tilemap` 一节借鉴的做法加。

## Consequences

- 一个关卡就是几个节点加几个类型化数组，不管多大都不会产生几万个节点；建图和改格子都很便宜，顶碎砖块可以直接 `eraseCell`。
- 每层每帧的 draw call 数等于屏幕内的区块数（实测 3 层约 21 个）。
- 一个 TileSet 只能用一张贴图：素材多时要在构建时合并成一张图集，或者拆成多个 TileSet 和图层。
- 碰撞只能是整格，做不了斜坡。
- 满屏不透明的图块层受 GPU 填充率限制（满地图 3 层时 56–58 fps，而 CPU 绘制只有 3.7 ms）。远景如果铺满整屏，应该换成一张背景图。
- 区块裁剪需要知道可见范围，所以 Camera2D 要和 TileMap 一起设计。
- `PixiRenderer` 多了一种需要同步的节点类型。

## Alternatives

- **每格一个 Sprite（或 Sprite2D 节点）**：真机上太慢，节点数也不可控。
- **区块容器 + 隐藏**：镜头移动时要重算组内所有精灵的变换，满地图仍然很慢。
- **每个区块一个 render group**：也够快，但比 Mesh 慢，建图慢 10 倍，每个区块还有几百个精灵对象常驻内存。
- **区块缓存成贴图（`cacheAsTexture`）**：每块约 5 MB 显存，区块进入屏幕时会卡一下。
- **镜头容器设为 render group**：平均变快，但区块进出屏幕时整组指令重建，出现 14–40 ms 的尖峰。
- **`@pixi/tilemap`**（5.0.2，支持 pixi 8）：读过源码，没有在真机上测。它是“绘制列表”：`tile(texture, x, y)` 往数组里追加记录，
  没有格子的概念，改一格要 `clear()` 后整张重建，也不做裁剪；用自定义渲染管线和着色器，每个图块的顶点数据约 208 字节（Mesh 方案 64 字节），
  多贴图着色器在 iOS WebGL1 上的表现未知。和“格子表 + 按格子碰撞”的节点模型对不上，用它还得在外面再包一层格子数据和区块管理，
  所以不用。但借鉴三个做法，需要时加进区块 Mesh：
  - 防接缝：每个图块的 uv 向内缩半个像素；还不够再在着色器里把采样坐标 clamp 在图块范围内（不用外扩图集）。
  - 动画图块在 GPU 上算：顶点里带上帧偏移和帧数，每帧只改一个 uniform，不逐格改 uv（需要自定义着色器）。
  - 翻转和 90° 旋转：用 pixi 的 `groupD8` 改写 uv。
- **像 Godot 一样生成 planck 静态物体**：几万格会变成大量碰撞形状，相邻格子的接缝还会卡住角色。见 ADR 0009。
