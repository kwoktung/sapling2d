# TileMap 渲染压测

问题：引擎要加 TileMap（横版平台游戏）。地图一层几千到几万格，在 iOS 小游戏（无 JIT、WebGL1）上用 Pixi 怎么画才能稳 60 fps？
改一格（顶碎砖块）要花多少？

## 场景

`src/bench.ts`，浏览器和小游戏共用。不经过引擎节点树，直接用 Pixi（初始化参数和 `PixiRenderer` 相同）。

- 地图 512 × 32 格，每格 16px，3 层（远景、地面、前景）。稀疏地图像真实关卡（约 1.2 万格），满地图每格都有图块（49152 格，最坏情况）
- 横屏，设计高度 270px（一屏约 17 行），宽度随屏幕比例；镜头在整张地图上来回扫（300 px/s），同时缓慢上下移动
- 镜头位置对齐到物理像素，图块用最近邻采样
- 每秒改 4 次地面层的格子（模拟顶砖块），比真实游戏频繁得多

画法：

| 画法 | 做法 |
|---|---|
| `sprites` | 每格一个 Sprite，全部放在一个容器里，不裁剪（基线） |
| `chunks` | 每 16×16 格一个容器，屏幕外的区块 `visible = false` |
| `groups` | 同 `chunks`，每个区块是 render group（`isRenderGroup`） |
| `mesh` | 每个区块一个 Mesh（容量固定 256 个四边形，空格子是退化四边形，16 位索引），屏幕外不显示 |
| `cached` | 同 `chunks`，屏幕内的区块 `cacheAsTexture`，离开屏幕就释放 |

每种画法再分两种：地图的父容器（“镜头”）是不是 render group（表里带 `+cam` 的是）。

## 运行

```sh
node spikes/tilemap/gen-tileset.mjs   # 重新生成图块集（已提交）
pnpm --filter example-sprite exec vite --config ../../spikes/tilemap/vite.config.ts
# 打开 http://localhost:5199/?mode=mesh&cam（可加 &fill、&extrude），或 ?sweep 跑全部（结果在 window.results）

# 真机
node spikes/tilemap/log-server.ts
WX_APPID=... SAPLING_RELEASE=1 SAPLING_LOG_URL=http://<局域网 IP>:7777/log \
  pnpm --filter example-sprite exec vite build -c ../../spikes/tilemap/vite.wechat.config.ts
```

真机依次跑 20 档（稀疏 / 满地图 × 镜头是否 render group × 5 种画法），每档 8 秒（前 2 秒预热），再加一档用外扩图块集的 `mesh+cam`；
每档结果 `console.log` 回传，稀疏地图的每档截一张图（`logs/`）。

列：`update` 是镜头和区块裁剪的耗时，`draw` 是 `renderer.render` 的 CPU 时间（WebGL 异步，GPU 跟不跟得上看帧间隔），
`calls` 是每帧 draw call 数，`edit` 是改一格本身的耗时（重建的开销落在下一帧的 `draw` 里，看 `draw` 的 p95）。

## 桌面冒烟（M1 Pro，Chrome，后台标签页）

只用来确认每种画法都能跑通。标签页在后台，帧由 MessageChannel 驱动（`&free`），计时精度只有 0.1ms，GPU 偶尔卡顿，**数字不可信**，只看量级：

| 画法 | 稀疏 draw ms | 满地图 draw ms | calls |
|---|---:|---:|---:|
| sprites | 1.25 | 6.83 | 1 |
| chunks | 0.65 | 5.02 | 1 |
| groups | 0.05 | 0.11 | 16–19 |
| mesh | 0.50 | 0.50 | 19 |
| cached | 0.69 | 5.59 | 2 |
| chunks+cam | 0.09 | | 2 |

看到的现象：满地图下 `chunks`（屏幕外区块已隐藏）几乎和不裁剪一样慢，而 `groups` 很快。
推测：镜头容器和区块在同一个 render group 里时，镜头每帧移动会让组内所有子节点（包括隐藏的）重算变换；
区块各自是 render group、或者镜头容器本身是 render group，移动镜头就只改组的变换。`chunks+cam` 稀疏地图从 0.65 降到 0.09 ms 支持这个推测，要在真机上确认。

### 分析

- **每格一个精灵、不分块不可用**：稀疏地图 draw 已经 9.4 ms（p95 19），满地图 19 fps。
- **按区块隐藏（chunks）不够**：满地图 draw 仍有 19.6 ms。桌面上的推测在真机上成立：镜头每帧移动，同一个 render group 里所有精灵都要重算变换。
- **镜头容器设成 render group（+cam）有副作用**：平均 draw 降了（sprites 9.4 → 3.0，chunks 5.6 → 1.7），但 p95 出现尖峰（chunks+cam 13.8，满地图 39.8）。
  区块进出屏幕会改 `visible`，整个镜头 render group 的指令要重建，组里的精灵越多尖峰越大。所以光靠镜头 render group 不行。
- **每个区块一个 Mesh 最好**：两种地图 draw 都最低、p95 最稳（3.5 / 4.5 ms），建图快一个数量级（20–38 ms，精灵要 300 ms 左右），
  改一格只改 16 个浮点数再上传一个 4 KB 的缓冲区（0.1 ms）。draw call 约 21 个（每层可见的区块数），完全可以接受。
  它不受镜头是不是 render group 的影响（2.6 vs 2.3）：一个 Mesh 对 Pixi 来说就是一个对象，镜头移动只改它的一个变换。
- **区块各自是 render group（groups）也稳**，但比 mesh 慢一些，建图慢 10 倍，每块还要几百个 Sprite 对象常驻内存。
- **缓存成贴图（cached）不划算**：满地图 draw 15.7 ms；进入屏幕的区块要重新渲染缓存（+cam p95 23.6）；
  每个缓存贴图约 1144² × 4 B ≈ 5 MB（区块 256px × 设备缩放 4.47），显存压力大。
- **满地图 mesh 的 fps 也只有 57–58，但 draw 只有 3.7 ms**：瓶颈在 GPU 填充率（3 层整屏不透明图块 × 874×402×9 物理像素 ≈ 950 万像素/帧），不是 CPU。
  真实关卡大部分是天空，问题不大；远景层如果是整屏图块，应该改成一张背景图（ParallaxLayer）。
- **16 位索引在 iOS WebGL1 上正常**（每个区块 1024 个顶点，`Uint16Array` 索引）。Pixi 默认用 `Uint32Array`，iOS 没有 `OES_element_index_uint`（PixiRenderer 的已知警告），这次没有测 32 位的情况，引擎实现时直接用 16 位。
- **接缝**：设备缩放 4.47（非整数）、镜头对齐物理像素、最近邻采样、不外扩的图块集，截图（`logs/tilemap-*.png`）上没有看到漏色或缝。
  不过截图时镜头在地图顶部，地面只露出一小块，等有了真实关卡再看一次。外扩图块集的那档性能没有差别，需要时可以用。
- 拆除时 Pixi 警告 “textureSource was destroyed while still bound to a shader”：先销毁了图块集的贴图源、后销毁 Mesh。
  引擎实现时要先销毁 Mesh（或者图块集的贴图源由资源系统管理，不跟着 TileMapLayer 销毁）。
- HUD 第一次刷新显示 1000 fps，是预热期间没有样本的显示问题，不影响结果。

## 结论

- **TileMapLayer 用“每个区块一个 Mesh”渲染**：区块 16 × 16 格；顶点缓冲区容量固定（256 个四边形），空格子写退化四边形；`Uint16Array` 索引；
  屏幕外的区块 `visible = false`；改格子只重写该格的 16 个浮点数并 `update()` 缓冲区。
- 这台 iPhone 17 上，3 层 512 × 32 的稀疏地图每帧绘制约 2.6 ms，满地图约 3.7 ms，都在预算内。
- 镜头（将来的 `Camera2D`）不需要为了 TileMap 设成 render group；它对普通精灵多的场景有没有好处要另外测，因为会带来指令重建的尖峰。
- 接入引擎：`PixiRenderer` 给 TileMapLayer 一个内容层（和 Sprite2D 的 sprite、Label 的 text 一样），里面放区块 Mesh；
  裁剪需要知道可见范围，也就是要先有 Camera2D（或者 TileMapLayer 从自己的全局变换和视口推算）。
